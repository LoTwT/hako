# 独立备份合同（refueling）

状态：**已实现、已部署（production，2026-10-04），首份真实备份读回通过；恢复写入仍未实现**。本文是该功能的唯一技术合同：状态模型、事务边界、调度、格式、保留策略、错误语义与验证证据。发布与首份真实备份证据见[发布记录](../releases/2026-10-04-independent-backup.md)；产品取舍（按变化备份、最近 30 份、故障期间继续同步）由[重新设计记录](./redesign.md#备份与恢复)维护；同步与账号语义见[账号同步合同](./account-sync.md)；设计依据与二次审查见[独立备份方案分析](../analysis/2026-10-03-independent-backup.md)。

## 1. 范围与部署前提

- 复用既有 `HakoAccountDurableObject`、`owner-account` 实例与 SQLite 库；增量建表，不新增 DO namespace、Queue、Workflow、Cron 或外部服务。
- 唯一新资源为私有 R2 Standard 桶绑定 `HAKO_BACKUPS`（桶名 `hako-backups-production`，声明于 [cloudflare.config.ts](../../cloudflare.config.ts)，`dev.remote: false`）；该桶已于 2026-10-04 创建并读回（Standard、私有、无公开访问），见[发布记录](../releases/2026-10-04-independent-backup.md)。
- 桶保持私有：无 `r2.dev`、自定义域名、浏览器 CORS、公开下载或持久 S3 Key；不设置按天 lifecycle 或与裁剪冲突的 bucket lock。
- 本地实现、验证与依赖均不升级锁文件版本；运行时绑定调用不产生入口请求，但 R2 操作计量真实存在。

## 2. 备份什么与版本判定

- 权威内容是 **DO 验证、合并后已持久保存的完整业务文档**：完整 Loro snapshot（记录 ID、合同字段、PeerID/操作 ID/因果历史及删除历史）。不重新创建 PeerID、不从当前 JSON 反建文档、不使用浅快照、不另存可写业务投影。字段校验复用[账号同步合同](./account-sync.md#同步接口-v1)的既有验证器，备份格式不复制字段清单。
- **不导出整个 DO SQLite**：身份映射、登录事务、会话、Token/verifier/Secret、Cookie、浏览器资料、草稿、本机确认游标与旧库导入映射一律不进入备份。
- 「变化」按合并前后 **OpLog 版本向量**判定：相同表示没有新增已保存操作；严格推进（包括被 LWW 隐藏的并发操作）表示新的服务端历史版本。不按当前值、保存点击、请求顺序或记录数量判等。
- 服务端 `revision` 只在提交成功的同步事务、或备份确认事务内的覆盖补登记（把确认时发现未覆盖的内容登记为新 revision）时递增（同一账号一个计数器）；合并窗口造成的缺号是正常结果，不能凭缺号判定丢失。`backupStreamId` 是启用时随机生成的序列标识，不是同步协议的文档代次。

## 3. 持久状态与两个事务边界

全部状态在既有账号 DO 的 SQLite 内，按账号（`account_id`）隔离：

| 状态 | 内容 |
| --- | --- |
| `backup_cursor` | stream、当前 revision、最近提交时间、最新完成 revision 与历史摘要、待备区间（起点/最新/首次时间/窗口到期）、清理重试计数与时间、固定 blocked 错误码 |
| `backup_frozen_task`(+chunks) | 唯一冻结任务：revision、捕获/提交时间、manifest 固定字节、包哈希与键、阶段内尝试计数与下次重试时间；原始快照按 512 KiB 分块 |
| `backup_completions` | 完成缓存：已验证对象的键/字节/哈希/记录数（常态 30 行，发布过程 31 行；不是恢复必需的唯一清单） |
| `backup_retention_check` | 「保留检查待完成」责任：确认完成时登记，检查与必要删除全部完成后才结清 |
| `backup_prune_plan` | 精确裁剪计划：每条待删 revision 的键与标记删除阶段 |

- **同步事务**：授权、账号匹配、输入校验、Loro 合并、主快照切换、revision 递增、待备责任更新与必要 `setAlarm` 在同一个 `storage.transaction()` 内提交或回滚（SQL 与 alarm 联合回滚已由 workerd 探针与本地集成验证证实）。类型错误先让外层事务完整回滚，再映射为既有失败响应；不通过 `waitUntil` 补任务；提交后继续 `await storage.sync()`，协议 1 持久确认语义不变。
- **捕获事务**：alarm 确认无冻结任务、无未收尾清理且窗口到期后，在同一短事务内读取主快照与 revision、创建唯一冻结任务（SQL 复制分块）、清除其覆盖的待备责任并安排安全唤醒；随后才在事务外做哈希、R2 与独立导入验证。冻结后任务字节不可替换。到期待备责任存在而权威主文档缺失时，不创建任务、不虚构空基线，事务回滚后进入 `invalid_source_document` blocked（保留责任与已有备份）。
- **覆盖补登记**（两个入口，其中确认入口在确认事务内原子执行）：空闲同步（无新历史）按当前合并结果、备份确认事务内按当前主文档，与「覆盖基准」的历史摘要比对——冻结任务在途时基准取其**冻结历史摘要**（最近的待发布上界，含启用基线尚无完成版本的路径），否则取最新完成备份的摘要；不一致（部署回退窗口写入、冻结任务在途期间旧版本写入、主表被外部替换）则在成功同步/完成确认的**当下**把该未覆盖内容登记为新的服务端 revision 并开启待备窗口（登记不触碰冻结字节与重试退避；确认入口与确认同事务——不存在「确认已提交、补登记未做」的崩溃窗口，登记写入失败则整个确认回滚重做），不长期停留在 coverage_mismatch 观察态、也不依赖未来的前台访问。已有待备或 blocked 时跳过；未准备的冻结任务（尚无摘要）由确认事务内入口兜底（任务在确认前必已准备、含冻结历史摘要）；摘要分析失败不阻塞调用方，缺口仍可由只读状态观察；重复相同结果不增版。
- **确认事务**：同一事务登记完成缓存、更新最新完成版本、释放冻结字节、清除自己覆盖的待备责任、**登记保留检查责任并保留 alarm**——即使尚未 LIST 或建立裁剪计划，重启后也必须先收尾，再捕获下一版（堵住出现第 32 份的崩溃窗口）。
- 常态存储界限：主快照 + 唯一冻结副本原始业务字节合计最多约 8 MiB，另计小型状态与表开销。

### 启用与基线

- 部署后账号的**首次成功同步事务**即启用：无服务端文档时 revision 1 进入待备窗口（含合法完整空快照，`recordCount: 0` 也是有效基线）；启用前已有文档时，同一提交把启用前快照冻结为基线任务（`reason: baseline`，`sourceCommittedAt: null`），若该次输入还推进历史，同时留下新版本的待备责任。
- 发布不会自动唤醒休眠 DO，也没有周期扫库；只读状态请求不建映射、不初始化、不上传。
- 「最近 30 份」指最近 30 份**完成且验证**的独立备份；每份完整快照仍包含更早业务历史，裁剪旧备份不等于清除历史。

## 4. 窗口、退避与唯一 alarm

- **固定 30 秒窗口**：首次未覆盖变化到达时 `dueAt = firstDirtyAt + 30s`，后续编辑只更新最新待备版本，不顺延窗口。窗口是调度目标，不是完成时限。
- 可重试失败退避：1、5、15、60 分钟，之后每小时。**每次 R2 尝试前**先持久递增尝试计数并安排安全重试，再做外部 I/O；新编辑不重置退避、不把故障重试提前；成功推进或整个任务完成后才复位。平台对 alarm 异常的最多 6 次重试不是唯一兜底，持久 `nextAttemptAt` 保证长期调度。
- 唯一 alarm 的优先级：**冻结任务 > 未收尾清理 > 窗口到期捕获**。一个 handler 只推进一个版本的有界生命周期（捕获→发布→保留收尾），下一个窗口由 alarm 另行安排。alarm 时间按与处理器相同的优先级从持久状态计算，不依据 `getAlarm()==null` 推断（运行中的 alarm 也可能返回 null）；构造只幂等建表，只读请求不做调度修复。
- **到期的重试/清理责任＝正当其时**：alarm 设为当前时间并立即由处理器消费（处理器持久的新责任总是未来时间）；普通同步不得把到期重试顺延或重开退避档（否则持续编辑会让备份永远无法重试）。立即循环的防护由**有界失败下限**承担：无法持久化新责任（含 blocked 持久化失败）的失败善后按当前尝试计数直接安排不早于下一档退避的未来 alarm，收尾调度不得把它覆盖成过去/立即 alarm。下限**持久于 `backup_cursor.retry_floor_at`**（与失败的任务写入异表），跨引擎重建仍生效——重启后、下限时间前的普通同步不得把失败退避中的重试提前到立即执行，共享 alarm 为其他账号触发时也不推进本账号的任何自动推进——重试、清理与待捕获 alike（处理器与调度器一致受下限约束，下限到期前的提前触发不推进、不重排、也不改写下限；主文档恢复后仍等到下限时间才捕获）；任何进度写入（新的未来责任、完成、结清）即解除下限；内存下限仅兜底下限写入本身失败的情形。到期的待备窗口表示「立即补捕获」（窗口是延迟目标，不是完成时限）。
- R2 I/O 期间不长期 `blockConcurrencyWhile`、不留未等待的上传 Promise；一次只有一个 R2 发布者；所有 R2 调用等待结果。

## 5. 包格式与对象布局

实现与严格解析的唯一来源是 [backup-format.ts](../../src/worker/backup/backup-format.ts)。要点：

- 键布局：`hako-backup/layout-v1/<environment>/accounts/<accountId>/refueling/<backupStreamId>/objects/<20位补零revision>-<bundleSha256>.hakobak` 与 `.../commits/<20位补零revision>.json`；环境标签固定 `production`。
- 二进制包：8 字节 `HAKOBK1\n` + 4 字节大端 manifest 长度 + UTF-8 JSON manifest + 原始 snapshot；总长精确匹配，无尾随数据。manifest ≤ 16 KiB，snapshot ≤ 4 MiB（沿用同步合同限额），标记 ≤ 4 KiB。
- manifest 固定字段顺序序列化；捕获时间、版本与 schema 一旦入库不再改变，重试不重新取时间或换编码。版本向量摘要规范：PeerID 与计数均为十进制字符串，按 PeerID 整数值排序（64 位精度不经 Number），无空白 JSON 二元组数组做 SHA-256。
- 完成标记是经过验证的不可变索引引用（格式、归属、精确键、字节与包哈希），在包读回验证之后才条件创建；manifest 与标记交叉核对一致。
- 条件创建用 `onlyIf: { etagDoesNotMatch: "*" }`（RFC 7232 `If-None-Match: *` 语义，本地 Miniflare R2 与官方合同一致）；**条件 PUT 返回 `null` 不是写入成功**，须读取原对象核对；读取前按对象上限检查长度，不做无界缓冲；ETag 不作为内容哈希。上传附带 SHA-256 校验，读回仍独立完整验证。

### 读回验证（发布完成标记前）

重新 GET 整包 → 长度与整体 SHA-256 → magic/格式严格解析 → manifest 与任务固定字节一致 → 归属（环境/账号/文档类型/序列/revision）匹配 → 快照长度与哈希 → 全新 Loro 导入（复用既有结构/业务校验、无 pending）→ 版本摘要与记录数核对。标记创建后同样读回核对确定内容。这证明验证时点可读、可解析且与捕获版本一致；不是恢复到生产应用的证明。

## 6. 序列防回退与归属检查

每次开始或恢复 R2 生命周期（任务尝试、保留检查、裁剪重试）都重新核对 R2：

- 新序列（尚无任何完成记录）首次接入时，枚举同环境下**全部账号前缀**：本账号文档前缀下只允许出现本任务自己的包与标记键，其他对象或未知序列 → `ownership_conflict`，不能因新生成 streamId/accountId 就把已有桶当空桶；只有**身份映射**能解释「同一 DO 的其他账号」——无映射的账号前缀（映射/状态全部丢失后重建，或仅映射丢失但游标仍在的孤儿账号）同样 → `ownership_conflict`，不静默另起新序列、遗弃旧账号的已有备份；多身份映射的账号合法共存。
- 已建立序列：每次任务生命周期在**任何新 PUT 之前**核对 `commits/`——每个标记键必须可解析且归属本序列、revision 可由完成缓存或当前冻结任务解释，且完成缓存中的每个版本必须仍有标记在 R2（仅本任务自己的 revision 允许缺失：首次创建尚未写入或重试幂等）；不可解释的更高序号或缓存/标记镜像不一致 → `sequence_conflict`，先阻断，不在冲突后才写入新对象。
- 裁剪重试（无论是否已有持久计划）先重新列出标记、重算保留集合，并核对完整应保留集合与完成缓存的镜像：只有当前精确计划能解释的待删标记缺失（含删除响应丢失）才可继续；其他保留标记缺失（外部删除或元数据回退）立即停止破坏性步骤、保留计划与剩余对象并进入 `sequence_conflict`。随后核查待保留对象的存在、长度与哈希；**旧验证结果不能无限期授权删除**。

## 7. 保留与裁剪

- 保留最近 30 份完成且验证的备份；无变化不新增，不按天到期。候选必须同时具有内容一致的标记与包，以 R2 `commits/` 清单为准（严格分页），DO 完成缓存只是调度镜像。
- 超出时：先在 DO 持久登记精确裁剪计划，再逐版**先删完成标记、后删包**，每步持久进展，最后重新列出确认集合已满足再在同一短事务结清保留责任。删除响应丢失/中断由原计划继续清理；不扩大成按前缀批量清空。
- 未触发裁剪时不做整套旧对象核查；触发裁剪时核查全部待保留对象（各一次标记与包 GET，即预算中的保守 B 类用量）。删除持续失败最多暂留 31 份：`cleanup_pending`、暂停下一份捕获、**同步继续**；修复后先收尾再追上最新。
- 保留集合缩小使某计划条目重新进入最近 30 份时结清计划而不删除；DO 元数据回退（缓存丢失、PITR）后不执行落后计划，未解释标记进入 blocked。

## 8. blocked 与错误语义

固定错误码：`content_conflict`（同键不同内容/读回校验不符）、`format_conflict`（未知或损坏格式）、`ownership_conflict`（未知归属）、`sequence_conflict`（不可解释序号/镜像不一致，含完成缓存有而 R2 标记缺失的外部删除或元数据回退）、`retention_verify_failed`（删除前核查失败）、`invalid_source_document`（待备责任的权威主文档在捕获时缺失，或冻结源文档无法独立导入验证）。

进入 blocked 后：保留冻结任务、旧备份与最新待备游标，**停止全部自动 R2 写入/删除并停止备份调度**；正常有效同步继续；状态接口持续报告。任何构造或正常调用不得自行解除 blocked；恢复由受控人工流程处理。

## 9. 只读状态接口

`GET /api/backups/refueling/status`（同源 Cookie，`no-store`）：重验会话并**只查已有映射**取得账号（无映射返回未初始化，不调用会创建映射的解析）；不续期、不写 Cookie、不初始化、不上传、不 LIST R2。字段：初始化状态、当前 revision、冻结任务 revision/字节、最新完成 revision、待备区间与首次时间、窗口到期、下次尝试、固定错误码、清理待完成数，以及「当前服务端版本是否已有已验证备份」——该项以**当前文档历史摘要与最新完成摘要比对**为准，不只看序号相等，避免旧代码回退期间的误报；无待备、无任务但摘要不一致时报告观察值 `coverage_mismatch`（不持久）。状态为服务器元数据，不覆盖设备离线修改；`uploading/retrying` 按任务尝试计数（≤1 视为上传中，>1 为退避重试中）。

## 10. 日志与计量

- 脱敏事件日志：捕获/重试/完成/裁剪失败/blocked 事件、backupId（stream:revision）、大小、耗时与错误码；不记录快照、字段值、真实身份、Cookie 或请求正文；复用既有 logs/traces，无新增监控服务。
- 每份备份的实际调用混合（合成引擎探针与 workerd 集成实测，单页无故障无人工读取）：按 [R2 定价](https://developers.cloudflare.com/r2/pricing/#class-a-operations)，**PUT 与 LIST 均计 A 类、GET 计 B 类、DELETE 免费**。未触发裁剪的一份为 PUT 2 + LIST 2 = **4 次 A 类**、GET 2（包与标记读回）= **2 次 B 类**、DELETE 0；触发裁剪的一份为 PUT 2 + LIST 4 = **6 次 A 类**、GET 62（2 次读回 + 30 份保留对象各 1 次标记与包核查）= **62 次 B 类**、DELETE 2（免费）。重试、多页与人工读取另计。实施前分析稿的 4 A / 64 B 是预算估计，实测差异（62 B）源于预算对保留核查次数的保守取整，以本条实测为准。
- 上述为 R2 操作计数。DO SQLite 的实际计量（workerd `rowsRead`/`rowsWritten`，[官方 SQL API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#sql-api) 的 cursor 计量随游标消费逐步累计，2026-10-04 集成验收实测、计量器按完整消费后取数）：生产节奏下一次同步（RPC 鉴证 + 合并 + 待备责任 + 续期判定）约 **6 行读 / 4 行写**；首份基线的备份生命周期（启用→捕获→发布→确认→保留收尾→重排，生产节奏单备份用例实测）约 **48 行读 / 18 行写 / 67 次 `sql.exec` 调用**；已有备份序列中的后续备份（窗口合并场景用例实测）约 **51 行读 / 18 行写 / 68 次 `sql.exec` 调用**——两者均为各自场景的稳定实测采样，行读差异来自场景差异（首份基线与含窗口合并的后续备份），不构成矛盾；触发裁剪的生命周期（retentionCount=2 加速实测；**非生产 30 份配置的计量，30 份场景未实测，不做总额线性放大**——其相对普通备份的增量 26 行读 / 5 行写 / 17 次调用中，只有逐份保留对象核查随保留数近似增长，计划登记、重新列出与结清为固定开销）约 **74 行读 / 23 行写 / 84 次 `sql.exec` 调用**；重试路径另测：失败尝试的生命周期（准备 + 失败 PUT + 善后重排）约 **27 行读 / 7 行写 / 34 次 `sql.exec` 调用**，成功重试的生命周期（记录尝试 + 序列核对 + 条件创建/读回 + 确认 + 覆盖核对 + 收尾）约 **40 行读 / 13 行写 / 52 次 `sql.exec` 调用**。「语句」口径为包装层捕获的 `sql.exec` 调用次数，非 SQLite 内部语句数。先前记录的 13/4、46/16、60/21 已**撤回**（计量器曾在游标消费前取数漏计行读，且同步取样区间混入调试查询；复审指出后修正计量器并重测）；49/18/69、75/23/86、41/13/54 为覆盖登记并入确认事务**之前**的采样，事务合并后已按连续多次全量运行稳定的重测值（上述 48/18/67、74/23/84、40/13/52，取自生产节奏单备份/裁剪/成功重试三个集成用例的 alarm 区间）替换。计量只在测试层统计（测试入口包装 `sql.exec`，按 alarm 生命周期差值取数并先冲刷未消费游标的计量微任务；**只读观测（/test/debug 轮询）被计量抑制排除，显式测试 SQL（/test/debug/sql 触发器与校准）单列到独立调试计数器**——交错在 alarm 外部 I/O 期间的观测轮询与调试 SQL 均不进入业务差值，同一业务不随调试/轮询频率变化，集成测试含确定性校准（alarm 等待期穿插调试 SQL 后业务计量精确不变；固定 3 次各 2 行调试读取使调试计数器精确 +6 行读/+3 调用且业务累计不变）；累计异常以 incomplete 显式标记（业务与调试计数器分别检查），标记时数值不采纳；生产 DO 类无计量代码），只覆盖包装层捕获的 `sql.exec`，不含 workerd 事务自身开销；上述为本地 workerd 观测读数（与生产账单同一计量 API 的本地值），**不是生产账单实测**；重试、空闲轮询与人工读取另计。表行数观察（如完成缓存 30 行）只是存储规模证据，不等价于上述计量。
